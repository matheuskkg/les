# 11. Visão de Implementação

A organização do código segue a Visão de Lógica (seção 9), e por isso não há diagramas adicionais aqui. Cada um dos dois projetos reflete o seu modelo. No back-end, o código se divide em pacotes de topo, um por módulo do sistema. Cada módulo tem as camadas de domínio, de aplicação e de infraestrutura, descritas na seção 7. Um pacote à parte, o compartilhado, guarda a infraestrutura comum a todos, como segurança, auditoria, carga inicial de dados e controle de tempo. No front-end, a aplicação web se divide em módulos de funcionalidade que espelham os módulos do back-end: sessão, catálogo, carrinho, checkout, conta, pedidos, notificações, administração e assistente. Há ainda um núcleo compartilhado com componentes de tela, utilitários e as chamadas à API. Uma verificação automática, parecida com a do back-end, impede que um módulo dependa de outro por caminhos não previstos (DEC-17).

Dois pontos diferem do fluxo de produção de um sistema real. O primeiro é a carga dos dados iniciais. Tabelas de apoio, livros, estoque, cupons, clientes e pedidos antigos não são cadastrados pela interface, porque o cadastro de livros e a entrada de estoque ficaram fora do MVP. Eles entram por scripts SQL executados em ordem na inicialização do back-end, nos dois bancos. O segundo é o perfil de testes de interface. Ele existe só no back-end e fica ativo apenas durante esses testes. Nele, a aplicação expõe rotas auxiliares que restauram os dados iniciais e controlam o relógio usado para expirar o carrinho, o que torna os testes repetíveis. Esse perfil não pode ser combinado com o PostgreSQL: a aplicação nem inicia nessa combinação (DEC-09).

O build junta as duas aplicações em um único arquivo de entrega. O Vite gera a versão compilada da aplicação web, e durante o empacotamento do back-end ela é copiada para dentro do arquivo final como arquivo estático. Assim, o comando java -jar entrega telas e API no mesmo processo, na porta 8080 (DEC-09). Se a aplicação web não tiver sido compilada antes, o arquivo sai apenas com a API. O processo de build do back-end não baixa o Node nem executa o front-end, o que evita depender de uma instalação extra durante o empacotamento.
